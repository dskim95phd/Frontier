제1장. 개발 배경 및 필요성
생성형 AI 서비스에서 추론 인프라는 지속적으로 유입되는 요청을 처리해야 하며, 메모리 자원은 처리량과 응답 지연, 운영 비용을 결정하는 주요 요소다. 특히 LLM 추론에서는 모델 가중치뿐 아니라 사용자 문맥을 유지하기 위한 KV 캐시가 메모리를 지속적으로 점유한다.
최근에는 모델과 워크로드가 빠르게 변화하는 동시에 추론 시스템의 규모도 확대되고 있다. 모델은 더 긴 컨텍스트를 지원하면서 KV 캐시를 효율적으로 구성하는 방향으로 발전하고 있으며, 워크로드는 긴 문서·코드 처리와 다중 턴 대화, 에이전틱 AI로 확대되고 있다. 또한 대규모 모델과 긴 컨텍스트를 처리하거나 높은 서비스 처리량을 확보하기 위해 여러 GPU를 병렬로 사용하는 구성이 중요해지면서, 메모리 사양의 영향도 개별 GPU가 아닌 시스템 수준에서 검토할 필요가 있다.
이에 따라 다양한 모델과 워크로드, multi-GPU 시스템 구성에서 메모리 병목과 자원 확장 효과를 비교할 수 있는 분석 체계가 필요하다.

1.1 모델 및 워크로드 변화
최근 LLM은 더 긴 컨텍스트를 지원하는 방향으로 발전하고 있다. 예를 들어, ChatGPT의 컨텍스트 윈도우는 2024년 128K에서 2025년 400K, 2026년 1M 까지 증가하였고, Deepseek v4, Kimi K3 등 다수의 공개 모델들도 현재 1M 컨텍스트를 지원하고 있다.
이러한 발전은 단순히 최대 컨텍스트 길이를 늘리는 데 그치지 않는다. GQA, MLA 등 새로운 어텐션 구조의 도입으로 동일한 컨텍스트 길이에서 필요한 KV 캐시 용량이 줄어드는 방향으로 발전하고 있다. 다만 메모리 절감 효과와 컨텍스트 길이에 따른 KV 캐시 증가 양상은 모델의 구조에 따라 조금씩 다르게 나타난다. 따라서 모델의 메모리 요구량을 평가할 때는 파라미터 수나 최대 컨텍스트뿐 아니라 어텐션 방식과 KV 캐시 구조까지 함께 고려해야 한다.

그림 1-1. 주요 어텐션 구조의 컨텍스트 길이에 따른 KV 캐시 용량.
워크로드 역시 변화하고 있다. 긴 문서 분석, 코드 생성 및 분석, 다중 턴 대화로 활용 범위가 확대되면서 입력 길이(Input Sequence Length, ISL)와 출력 길이(Output Sequence Length, OSL)의 다양성이 증가하고 있다.
특히 에이전틱 AI에서는 하나의 작업을 수행하는 동안 모델 호출과 도구 실행이 반복되므로 요청 길이뿐 아니라 동일 세션의 요청 간격도 중요한 특성이 된다. 실행시간이 제각기 다른 여러 도구의 호출로 인해서, 요청 간격도 더 넓은 범위를 갖게 된다.

그림 1-2. Agentic AI 워크로드
이처럼 최근 추론 환경은 모델 측면에서는 컨텍스트 길이와 KV 캐시 구조가 변화하고, 워크로드 측면에서는 ISL, OSL 및 요청 간격의 범위가 확대되는 방향으로 변화하고 있다.

1.2 기존 분석 방법의 한계
메모리 사양을 검토하는 가장 간단한 방법은 모델 구조와 대표적인 요청 길이, 동시 사용자 수를 이용한 정적 용량 계산이다. 정적 계산은 초기 규모를 빠르게 추정하고 계산 로직을 검증하는 데 유용하지만, 실제 요청의 도착과 종료, 요청 간 중첩, KV 캐시의 생성·재사용·제거와 같은 상태 변화를 표현하기 어렵다.
예를 들어 평균 요청 길이를 기준으로 용량을 산정하면 긴 요청이 동시에 활성화되는 상황을 과소평가할 수 있다. 반대로 최대 요청 길이와 최대 동시성을 기준으로 하면 실제 운영에서 거의 사용되지 않는 자원까지 포함하여 과도한 사양을 산정할 수 있다.
에이전틱 워크로드에서는 요청 간격도 함께 고려해야 한다. 후속 요청이 빠르게 발생하면 기존 KV 캐시를 재사용할 수 있지만, 그 사이 다른 세션의 요청이 유입되면서 캐시가 제거되면 이후 문맥 재계산이 필요할 수 있다. 따라서 메모리 용량 변화가 캐시 재사용과 재계산, 응답 지연에 미치는 효과는 요청 흐름과 시스템 상태를 함께 고려해야 한다.
분석 대상 시스템도 단일 GPU에서 여러 GPU를 사용하는 multi-GPU 환경으로 확대되고 있다. 대규모 모델은 모델 가중치와 KV 캐시를 여러 GPU에 분산하여 처리하며, 요구 처리량에 따라 여러 GPU와 모델 복제본을 함께 사용할 수 있다. 이 경우 개별 GPU의 메모리 용량과 성능만으로는 실제 시스템의 병목을 충분히 설명하기 어렵다. 여러 GPU와 메모리 계층, 네트워크에서 발생하는 자원 사용과 데이터 이동을 하나의 시스템으로 평가해야 한다.
실장비 측정은 가장 직접적인 검증 방법이지만 다양한 GPU 수, 메모리 용량·대역폭 및 서빙 구조를 반복적으로 평가하기에는 비용과 시간이 많이 필요하며, 아직 존재하지 않는 차세대 플랫폼에는 적용할 수 없다. 공개 벤치마크 역시 특정 하드웨어와 소프트웨어 구성에 종속되어 있어 개별 자원의 영향을 독립적으로 변화시키며 분석하기 어렵다.
따라서 시간에 따른 요청과 캐시 상태의 변화뿐 아니라 multi-GPU 환경에서 여러 GPU와 메모리·네트워크 자원의 상호작용을 함께 반영하면서 다양한 설계 조합을 빠르게 비교할 수 있는 분석 방법이 필요하다.

1.3 고수준 시뮬레이터 Frontier
본 개발에서는 이러한 목적을 위해 rack-scale LLM inference를 대상으로 하는 고수준 이산 사건 시뮬레이터 Frontier를 개발하였다. 개별 GPU 명령이나 커널 내부 동작을 모두 재현하여 아주 높은 정확도를 보장하는 시뮬레이터를 이런 rack-scale의 시스템을 분석에 사용하는 것은 실행시간 관점에서 현실적으로 불가능하다. 반면 Frontier는 합리적인 수준의 정확도로 장시간 워크로드와 큰 시스템을 다양한 구성에 대해 빠르게 비교하여 병목을 찾아내는 것을 목표로 한다.
Frontier는 초기 설계 단계에서 다음과 같은 질문에 정량적인 근거를 제공하는 것을 목표로 한다.
•	어떤 조건에서 HBM 용량 또는 대역폭 병목이 발생하는가
•	CPU DRAM을 추가할 때 KV 캐시 재계산과 서비스 성능이 얼마나 개선되는가
•	GPU 수와 병렬화 구성을 변경할 때 메모리 병목은 어떻게 달라지는가
특히 Frontier가 답하고자 하는 핵심 질문은 다음과 같다.
주어진 모델과 워크로드를 rack-scale 시스템에서 운영할 때 메모리 병목은 어디에서 발생하며, HBM과 CPU DRAM의 용량·대역폭 및 시스템 구성을 어느 수준까지 확장해야 서비스 성능이 유의미하게 개선되는가?
Frontier를 활용하면 실장비가 없는 초기 기획 단계에서 넓은 설계 공간을 탐색하고, 이후 상세 분석과 실측을 집중할 후보 구성을 선정할 수 있다. 본 개발의 목적은 특정 모델이나 플랫폼의 일회성 최적값을 찾는 것이 아니라, 모델과 워크로드 및 시스템 구성이 변화하더라도 동일한 기준으로 병목과 메모리 설계 대안을 비교할 수 있는 분석 체계를 확보하는 데 있다.
제2장에서는 Frontier의 분석 범위, rack-scale 시스템 모델 및 분석 방법을 설명한다.
