# 제2장. Frontier 시뮬레이터 구성 및 분석 방법

본 장에서는 Frontier의 시뮬레이션 구조와 동작 방식, 시스템 구성, 분석 지표 및 구현 범위를 설명한다.

## 2.1 시뮬레이터 구조 및 동작 개요

Frontier는 rack-scale LLM 추론 시스템을 대상으로 하는 고수준 이산 사건 시뮬레이터다. 워크로드와 모델, 시스템 구성을 입력으로 받아 여러 GPU에서 발생하는 요청 처리와 자원 상태 변화를 시간축에서 재현하고, 메모리 사용과 서비스 성능을 분석한다.

Frontier는 GPU의 개별 명령이나 커널 내부 동작을 직접 재현하지 않고, **모델의 layer 실행과 시스템 간 데이터 전송을 주요 실행 단위로 추상화**한다. 이를 통해 단일 GPU의 세부 동작보다 여러 GPU에서 연산과 통신, 메모리 사용이 상호작용하는 rack-scale 시스템의 동작을 효율적으로 모델링한다.

시간 진행에는 이산 사건 시뮬레이션(Discrete-Event Simulation, DES)을 사용한다. 요청 도착, layer 실행 완료, network 또는 KV 데이터 전송 완료와 같이 시스템 상태가 변하는 시점을 event로 정의하고 이를 발생 시간 순서대로 처리한다.

각 event가 처리될 때 GPU 및 네트워크의 가용 상태, 요청의 실행 위치와 진행 상태, KV 캐시와 메모리 점유 상태를 갱신한다. 이후 모델 구조와 병렬화 방식, 서빙 정책에 따라 다음 layer 실행 또는 데이터 전송 event를 생성한다.

```text
요청 도착
    ↓
Layer 실행 event
    ↓
필요 시 통신·데이터 전송 event
    ↓
다음 Layer 실행 event
    ↓
        ...
    ↓
요청 완료
```

예를 들어 여러 GPU에 분할된 모델을 실행할 경우 각 layer의 연산과 병렬화에 필요한 통신이 순차 또는 병렬 event로 구성된다. 프리필-디코드 분리형에서는 프리필 완료 이후 KV 전송이 별도의 network event로 발생하며, CPU KV 오프로딩에서는 GPU와 CPU DRAM 간 저장 및 복원 과정이 데이터 전송 event로 반영된다.

이러한 event의 실행 시간과 자원 사용은 설정된 모델 및 시스템 조건으로부터 결정된다. 여러 요청이 동시에 진행되는 경우에는 각 GPU와 네트워크 자원의 가용 시점에 따라 event의 시작과 완료 시점이 달라지며, 이에 따라 대기 시간과 메모리 점유도 함께 변화한다.

이를 통해 Frontier는 세부 커널 수준까지 재현하지 않으면서도 **rack-scale 환경에서 연산, 통신, 메모리 상태가 시간에 따라 상호작용하는 과정**을 모델링한다. 시뮬레이션 과정에서 기록된 자원 상태와 요청별 처리 결과는 이후 메모리 병목과 서비스 성능 분석에 사용한다.
## 2.2 시스템 구성

Frontier의 분석 대상 시스템은 하드웨어 및 네트워크, 모델 및 실행 특성, 서빙·병렬화 구조, 요청 라우팅 및 스케줄링, KV 캐시 및 메모리 계층으로 구성한다. 각 설정은 시뮬레이션에서 발생하는 layer 실행과 데이터 전송 event, GPU별 메모리 상태 및 요청 처리 과정에 반영된다.

### 2.2.1 하드웨어 및 네트워크

GPU 종류와 대수, GPU당 HBM 용량·대역폭 및 연산 성능을 설정한다. 네트워크는 노드 내부와 노드 간 연결의 대역폭과 지연을 입력한다.

내장된 장비 사양을 사용하거나 개별 수치를 변경하여 차세대 또는 가상 장비를 구성할 수 있다. 프리필과 디코드를 별도 GPU 그룹에서 수행하는 경우에는 각 그룹의 장비 사양을 별도로 설정한다.

GPU 사양은 layer 실행 시간과 모델·KV 캐시의 수용 가능 용량을 결정하는 데 사용되며, 네트워크 사양은 병렬화 통신과 KV 데이터 이동에 따른 전송 시간을 산정하는 데 사용된다.

### 2.2.2 모델 및 실행 특성

모델 설정에는 계층 수, 어텐션 구조, MoE 전문가 구성 및 KV 캐시 형식이 포함된다. 가중치와 KV 캐시의 정밀도도 함께 설정하며, 이를 기반으로 GPU별 모델 가중치와 KV 캐시 크기, layer별 연산량 및 메모리 전송량을 산정한다.

Layer 실행 시간은 확보된 측정값을 직접 사용할 수 있으며, 측정값이 없는 경우에는 모델 연산량과 GPU의 연산 성능·메모리 대역폭을 이용해 산정한다. 이에 따라 실장비가 존재하는 플랫폼에서는 측정값을 활용하고, 차세대 또는 가상 플랫폼에서는 예상 사양을 이용하여 분석할 수 있다.

모델의 어텐션 및 KV 구조는 토큰 증가에 따른 KV 캐시 크기와 데이터 이동량에도 반영된다.

### 2.2.3 서빙 및 병렬화 구조

LLM 요청은 입력 문맥을 처리하는 프리필(prefill)과 출력 토큰을 생성하는 디코드(decode) 단계로 구성된다. Frontier는 두 단계를 동일한 GPU 그룹에서 수행하는 통합형(co-location)과 별도의 GPU 그룹에서 수행하는 프리필-디코드 분리형(Prefill-Decode Disaggregation, PDD)을 지원한다.

| 구조 | 구성 | 주요 영향 |
| --- | --- | --- |
| 통합형 | 동일 GPU 그룹에서 프리필과 디코드 수행 | 두 단계가 연산 및 메모리 자원을 공유 |
| PDD | 프리필과 디코드를 별도 GPU 그룹에 배치 | 단계별 자원 구성 가능, KV 전송 및 그룹 간 처리 균형 필요 |

PDD에서는 프리필 완료 후 KV 데이터가 디코드 GPU 그룹으로 전달되어야 하며, Frontier는 이를 별도의 network transfer event로 모델링한다.

rack-scale 환경에서 모델과 요청을 여러 GPU에 배치하기 위한 주요 병렬화 방식도 지원한다.

| 방식 | 기본 개념 | 주요 영향 |
| --- | --- | --- |
| TP | 하나의 layer 연산을 여러 GPU에 분할 | GPU당 연산·메모리 부담 감소, collective 통신 발생 |
| PP | 모델 layer를 여러 stage에 분할 | GPU당 가중치 부담 감소, stage 간 데이터 전송 발생 |
| DP | 모델 복제본에 서로 다른 요청을 분산 | 전체 처리량 증가, 복제본별 가중치 저장 |
| EP | MoE 전문가를 여러 GPU에 분산 | 전문가별 메모리 분산, 토큰 교환 발생 |
| DCP | 디코드 문맥을 여러 GPU에 분산 | GPU당 KV 부담 감소, 문맥 관련 통신 발생 |

실제 시스템에서는 여러 병렬화 방식을 조합하며, 구성에 따라 layer 실행을 담당하는 GPU와 필요한 통신 event, GPU별 가중치 및 KV 캐시 배치가 달라진다.

### 2.2.4 요청 라우팅 및 스케줄링

rack-scale 시스템에서는 유입된 요청을 처리 가능한 model replica 또는 GPU group으로 배분하고, 각 serving group에서 실행할 요청을 지속적으로 선택해야 한다.

Frontier는 구성된 라우팅 정책에 따라 요청을 적절한 serving group으로 전달하고, 각 그룹 내부의 요청 처리 과정은 vLLM V1의 주요 scheduling 동작을 기준으로 모델링한다. 요청은 도착 후 대기열에 등록되며, 사용 가능한 메모리와 배치 한도 내에서 실행 중인 요청과 신규 요청을 함께 구성하는 continuous batching 방식으로 처리한다.

Continuous batching에서는 하나의 고정된 batch가 전체 요청이 종료될 때까지 유지되지 않는다. 요청이 완료되면 해당 자리에 대기 중인 요청을 추가할 수 있으며, 이를 통해 요청별 길이가 서로 다른 환경에서도 GPU 자원을 지속적으로 활용할 수 있다.

![요청 라우팅 및 continuous batching 개념도](../presentation_assets/request-routing-continuous-batching.svg)

> **그림 2-X.** 요청 라우팅 및 continuous batching 개념도. 유입된 요청은 serving group으로 배분되며, 각 그룹에서는 실행 중인 요청의 완료와 신규 요청의 도착에 따라 batch 구성이 시간에 따라 변경된다.

배치당 최대 요청 수와 토큰 수 등의 설정은 각 시점에 함께 처리할 수 있는 요청의 범위를 결정한다. 긴 입력을 여러 구간으로 나누어 처리하는 chunked prefill 역시 필요에 따라 적용할 수 있다.

### 2.2.5 KV 캐시 및 메모리 계층

LLM 추론에서는 요청 처리 과정에서 생성된 KV 캐시가 GPU HBM을 점유하며, 동일 세션의 후속 요청에서는 기존 문맥의 KV 캐시를 다시 사용할 수 있다. Frontier는 요청과 세션 정보를 기반으로 KV 캐시의 생성, 유지 및 재사용을 추적한다.

GPU HBM의 가용 공간이 부족해지면 모든 KV 상태를 계속 유지할 수 없으므로 캐시 축출이나 요청 preemption이 발생할 수 있다. 필요한 KV 상태가 GPU에 존재하지 않는 경우에는 이전 문맥을 다시 계산해야 하며, 이러한 재계산은 추가 연산과 응답 지연으로 반영된다.

Frontier는 GPU HBM 외에 CPU DRAM을 추가적인 KV 캐시 계층으로 사용할 수 있다. GPU에서 제거되는 KV 캐시를 CPU DRAM에 저장하고 후속 요청에서 필요할 때 다시 GPU로 복원하며, 이 과정에서 CPU DRAM의 가용 용량과 GPU–CPU 간 전송 대역폭 및 지연을 함께 반영한다.

```text
                    후속 요청
                       │
                       ▼
              ┌─────────────────┐
              │ KV in GPU HBM?  │
              └───────┬─────────┘
                  Yes │ No
                      │
            ┌─────────┘
            ▼
        KV 재사용              CPU DRAM에 존재
                                 │
                         ┌───────┴───────┐
                        Yes              No
                         │                │
                         ▼                ▼
                     KV 복원          문맥 재계산
```

> **그림 2-X.** KV 캐시 재사용 및 메모리 계층의 개념. 후속 요청에서 필요한 KV 상태가 HBM에 존재하면 직접 재사용하고, CPU DRAM에 저장되어 있으면 복원한다. 캐시가 남아 있지 않은 경우에는 이전 문맥을 재계산한다.

이러한 메모리 계층의 동작을 통해 HBM 용량 증가, CPU DRAM 추가 및 데이터 전송 대역폭 변화가 캐시 적중률과 재계산량, 최종 서비스 성능에 미치는 영향을 비교할 수 있다.

## 2.3 분석 지표 및 절차

Frontier는 메모리와 시스템 구성의 변화가 KV 캐시와 요청 처리에 미치는 영향을 분석하고 이를 서비스 성능 지표와 연결한다.

```text
메모리·시스템 구성 변화
          ↓
KV 캐시 점유·축출·재계산 및 데이터 이동
          ↓
      대기 및 처리 효율 변화
          ↓
      응답 지연·처리량 변화
```

주요 분석 지표는 다음과 같다.

| 분석 영역 | 주요 지표 | 분석 목적 |
| --- | --- | --- |
| GPU 메모리 | KV 캐시 점유, 최대 점유량, 메모리 여유 | HBM 용량 병목 및 필요 용량 확인 |
| 캐시 및 재계산 | 캐시 적중·축출, 요청 중단, 재계산 토큰 | 메모리 부족에 따른 추가 연산 확인 |
| CPU DRAM | CPU 캐시 점유·적중, GPU-CPU 전송량 및 지연 | CPU DRAM 용량·대역폭 효과 분석 |
| 시스템 | GPU 그룹별 자원 사용, 통신량 및 대기 | 자원 불균형 및 rack-scale 병목 확인 |
| 서비스 성능 | 처리량, TTFT, TPOT, 전체 응답 시간 | 자원 변경 효과를 서비스 수준에서 평가 |

응답 지표는 평균과 함께 p50·p90·p99를 확인하여 일반적인 요청과 지연이 큰 요청을 구분한다.

구성 비교는 다음 절차로 수행한다.

1. 대상 워크로드와 기준 시스템을 구성한다.
2. HBM, CPU DRAM, GPU 수, 전송 대역폭 또는 시스템 구성 중 분석 변수를 선정한다.
3. 대상 변수를 단계적으로 변경하면서 동일한 워크로드를 반복 실행한다.
4. 메모리 상태, 캐시 재사용·재계산, 데이터 이동 및 서비스 성능을 비교한다.
5. 서비스 목표를 만족하는 후보와 자원 확장의 효과가 큰 구간을 확인한다.
6. 개선 효과가 포화되거나 병목이 다른 자원으로 이동하는 지점을 확인한다.
7. 후보 구성을 상세 시뮬레이션 또는 실장비 검증 대상으로 선정한다.

단일 지표가 가장 높은 구성을 자동으로 최적안으로 판단하지 않는다. 서비스 수준 목표를 만족하는 범위에서 자원 증가에 따른 성능 개선과 시스템 병목의 변화를 함께 평가한다.[^frontier-paper]

## 2.4 개발 과정 및 적용 범위

본 개발에서 구축한 C++ 시뮬레이터는 기존 프로젝트와 구분하여 **ServeWeaver**라 명명하였다. ServeWeaver는 처음부터 모든 구조를 새로 설계한 것은 아니며, Microsoft가 오픈소스로 공개한 Vidur와 이를 기반으로 확장된 Frontier를 참고하여 개발하였다. 두 시뮬레이터에서 사용한 이산 사건 기반의 요청·배치·스케줄링 모델은 ServeWeaver의 출발점이 되었으며, 기존에 검증된 개념과 동작은 가능한 범위에서 유지하였다.[^serveweaver-lineage]

Vidur와 기존 Frontier는 Python을 중심으로 구현되어 있어 기능을 이해하고 확장하기에는 편리했지만, 장시간 워크로드와 수십 개 GPU로 구성된 rack-scale 시스템을 반복 분석할 때에는 실행시간 부담이 컸다. 특히 CPU DRAM 용량이나 요청 주입률처럼 여러 변수를 바꾸어 수십 개의 조합을 비교하려면 하나의 실행 속도뿐 아니라 전체 실험을 완료하는 시간도 중요하다. 이에 ServeWeaver는 시뮬레이션의 핵심 기능을 C++로 전면 재작성하였다. 이는 Python 코드를 한 줄씩 옮기는 방식이 아니라, 기존의 주요 동작을 기준으로 event 처리, 상태 관리, 스케줄링 및 메모리 모델을 C++ 구조에 맞게 다시 구성한 것이다.[^cpp-transition]

재작성 결과, 동일 입력을 사용한 내부 비교에서 기존 Python 구현보다 10배 이상의 실행 속도 향상을 확인하였다. 한 기준 실험에서는 16,333초, 즉 약 4.54시간의 가상 서비스 운영과 93,571개의 완료 요청을 실제 시간 347.72초에 재현하였다.[^performance-example] 실행시간은 워크로드와 시스템 구성에 따라 달라지지만, 이러한 속도 개선을 통해 12시간 규모의 워크로드와 여러 메모리·부하 조합을 현실적인 시간 안에 반복 분석할 수 있게 되었다.

기존 시뮬레이터에 구현되어 있던 스케줄링, continuous batching, 프리필-디코드 분리 및 주요 병렬화 기능도 최신 모델에 적용할 수 있도록 확장하였다. 기존 기능의 상당 부분은 일반적인 MHA 구조를 중심으로 설계되어 있었기 때문에 MLA나 KDA를 사용하는 모델에서는 KV 캐시의 크기와 GPU별 저장 방식을 그대로 적용하기 어려웠다. 예를 들어 MHA는 TP를 적용할 때 KV 캐시를 attention head 단위로 나눌 수 있지만, MLA의 압축된 KV 상태는 여러 head가 함께 사용하므로 TP GPU마다 동일한 상태를 보유해야 한다. ServeWeaver는 이 문제에 대응하기 위해 문맥의 token 방향으로 KV 캐시를 나누는 DCP를 지원하고, 이에 맞추어 GPU별 KV 용량과 데이터 이동을 계산하도록 수정하였다. 또한 KDA와 MLA가 함께 사용되는 모델에서는 token에 따라 증가하는 KV 상태와 세션 단위의 고정 상태를 구분하여 반영하도록 모델을 확장하였다.

기존 구현에 없던 기능도 새롭게 추가하였다. 대표적으로 CPU KV 오프로딩은 GPU HBM에서 제거되는 KV 캐시를 CPU DRAM에 저장하고, 후속 요청이 도착했을 때 이를 다시 GPU로 복원하는 전 과정을 모델링한다. CPU DRAM의 용량뿐 아니라 GPU–CPU 간 전송 대역폭과 지연, 캐시 축출 및 복원 여부를 함께 반영하므로 CPU 메모리 증설이 실제 처리량과 응답시간 개선으로 이어지는지를 평가할 수 있다. 또한 하나의 독립 요청만 처리하던 워크로드 모델을 확장하여, 여러 요청이 시간 간격을 두고 이어지는 멀티턴 세션을 지원하였다. 이를 통해 이전 대화 문맥을 반복 사용하는 코딩 에이전트와 같은 에이전틱 AI 워크로드의 KV 캐시 재사용과 장시간 메모리 점유를 분석할 수 있게 되었다.

현재 ServeWeaver의 C++ 본체는 테스트 코드를 제외하고 약 3.1만 줄 규모로 구성되어 있다.[^serveweaver-code-size] 구현 과정에서는 개별 계산 기능에 대한 단위 테스트와 함께 요청 도착부터 완료까지의 통합 테스트, 기존 결과가 유지되는지를 확인하는 회귀 테스트, 다양한 모델과 시스템 구성을 조합한 장시간·대규모 테스트를 수행하였다. 특히 dense 및 MoE 모델, online 및 offline 실행, 서로 다른 요청 길이와 부하, 기능 활성화 여부와 병렬화 구성을 함께 점검하여 특정 실험에만 맞는 동작이 되지 않도록 검증하였다.

현재 C++ 코어는 통합형 및 순차형 PDD, TP·PP·DP·EP·DCP, 멀티턴 세션 캐시, MLA 및 KDA·MLA 하이브리드 모델, CPU KV 오프로딩을 주요 분석 범위로 한다. 일부 sparse attention, 어텐션-FFN 분리 및 speculative decoding 등은 아직 포함하지 않는다.[^implementation-contract] 또한 시뮬레이터의 절대 처리량과 지연은 입력한 장비 성능과 모델링 가정의 영향을 받으므로, 최종 사양 결정 전에는 확보 가능한 실측값이나 상세 분석을 이용한 보정이 필요하다. 제3장에서는 HBM과 CPU DRAM의 용량을 변경한 사례를 통해 ServeWeaver의 분석 결과와 설계 판단 과정을 설명한다.
