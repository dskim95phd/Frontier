# 제2장. 시뮬레이터 소개

제1장에서는 모델 구조와 고객의 사용 패턴에 따라 추론 시스템의 메모리 요구량이 계속 달라지며, 실제 장비가 없는 단계에서 여러 설계안을 비교할 수 있는 분석 수단이 필요함을 설명하였다. 본 장에서는 이러한 목적으로 개발한 Frontier의 역할, 분석 대상 및 활용 방법을 정리한다.

## 2.1 개발 목적과 분석 흐름

Frontier는 고객의 LLM 추론 서비스를 가상 환경에서 운영해 보는 고수준 시뮬레이터다. 모델, 시스템 구성 및 고객 트래픽을 입력하면 개별 요청의 처리 과정과 메모리 변화를 시간 순서대로 재현하고, 메모리 사양 변경이 서비스 성능에 미치는 영향을 비교한다.

분석 흐름은 다음과 같다.

| 구분 | 주요 내용 |
| --- | --- |
| 입력 | 모델 구조, GPU와 메모리 사양, 시스템 구성, 요청별 입력·출력 길이와 도착 시각 및 세션 정보 |
| 가상 운영 | 요청 도착과 대기, 배치 처리, KV 캐시 사용, 데이터 전송 및 요청 완료를 시간축에서 재현 |
| 분석 결과 | 메모리 부족 시점과 원인, 재계산량, 응답 지연과 처리량, 메모리 증설 효과 및 후보 구성 |

고객 트래픽은 평균값이 아니라 요청 단위로 입력한다. 따라서 짧은 요청과 긴 요청이 섞인 분포, 특정 시간대의 요청 집중 및 동일 세션의 불규칙한 요청 간격을 그대로 반영할 수 있다. 모델과 시스템 구성은 트래픽과 별도로 관리하므로 동일한 고객 워크로드에서 장비, 메모리 용량 또는 운영 정책만 변경한 비교도 가능하다.

```text
고객 워크로드 + 모델 + 시스템 구성
                  ↓
         Frontier 가상 운영
                  ↓
메모리 병목 식별 + 서비스 영향 분석 + 후보 설계 선별
```

이 분석을 수행하려면 모델과 장비뿐 아니라 서빙 구조, 병렬화 및 운영 정책을 하나의 시스템으로 구성하고, 요청 처리 과정에서 발생하는 상태 변화를 시간축으로 재현해야 한다. 제2.2절과 제2.3절에서는 각각 시스템 구성 항목과 시뮬레이션 방식을 설명한다.

## 2.2 시스템 구성 항목

분석 대상 시스템은 하드웨어, 모델, 서빙 구조, 병렬화 및 운영 정책으로 구성한다. 각 항목은 독립적으로 변경할 수 있으며, 변경된 조건은 GPU별 메모리 여유, 데이터 전송량, 요청 처리 순서 및 응답 성능에 반영된다.

### 2.2.1 GPU 및 네트워크 설정

GPU 종류와 대수, GPU당 HBM 용량·대역폭 및 연산 성능을 설정한다. 네트워크는 노드 내부와 노드 간 연결의 대역폭 및 지연을 입력한다. 내장된 장비 사양을 사용하거나 개별 수치를 변경해 차세대 또는 가상 장비를 구성할 수 있으며, 프리필-디코드 분리형에서는 두 장비 그룹의 사양을 각각 설정할 수 있다.

이 설정은 모델과 KV 캐시를 수용할 수 있는지, 연산과 데이터 이동 중 어느 부분이 병목이 되는지를 판단하는 기준으로 사용한다.

### 2.2.2 모델 및 실행 설정

모델 설정에는 계층 수, 어텐션 구조, MoE 전문가 구성 및 KV 캐시 형식이 포함된다. 연산과 가중치·KV 캐시의 정밀도도 함께 설정하며, 이 값은 GPU별 가중치와 KV 캐시 크기, 연산량 및 메모리 전송량에 반영된다.

실행 시간은 확보된 측정값을 직접 입력하거나, 모델 연산량과 GPU의 연산 성능·메모리 대역폭을 이용해 산정할 수 있다. 이에 따라 실장비가 있는 플랫폼은 측정값을 활용하고, 차세대 또는 가상 장비는 예상 사양을 이용해 비교한다.

### 2.2.3 서빙 구조

LLM 요청은 입력 문맥을 처리하는 프리필(prefill)과 출력 토큰을 생성하는 디코드(decode) 단계로 구성된다. 두 단계를 동일한 장비에서 수행하는지, 별도 장비 그룹으로 분리하는지에 따라 시스템 구성이 달라진다.

| 구조 | 구성 | 주요 검토 사항 |
| --- | --- | --- |
| 통합형 | 동일한 GPU 그룹이 프리필과 디코드를 모두 처리 | 구성이 단순하지만 두 단계가 연산과 메모리를 함께 사용 |
| 프리필-디코드 분리형(PDD) | 프리필과 디코드를 별도 GPU 그룹에 배치 | 단계별 자원 조정이 가능하지만 두 그룹의 처리 균형과 KV 데이터 전송을 고려해야 함 |

분리형 구조에서는 프리필이 완료되고 KV 데이터가 전달된 후에 디코드를 시작할 수 있다. 따라서 한쪽 장비 그룹의 지연이나 메모리 부족은 데이터 전달 시점과 다른 장비 그룹의 대기 상태에도 영향을 준다. Frontier는 두 장비 그룹을 독립적으로 운영하면서 이 연결 관계를 함께 재현한다.[^frontier-paper]

### 2.2.4 병렬화 방식

대형 모델은 한 대의 GPU에 모두 배치하기 어렵기 때문에 모델과 요청을 여러 GPU에 나누어 처리한다. 세부 병렬화 기법은 다음 세 범주로 정리할 수 있다.

| 구분 | 기본 개념 | 메모리·성능 영향 |
| --- | --- | --- |
| 모델 분할(TP·PP) | 모델의 연산이나 계층을 여러 GPU에 분산 | GPU당 가중치 부담은 줄지만 GPU 간 통신이 증가 |
| 요청 분산(DP) | 동일한 모델 복제본이 서로 다른 요청을 처리 | 전체 처리량은 늘지만 복제본마다 가중치를 저장해야 함 |
| 전문가·문맥 분할(EP·DCP) | MoE 전문가 또는 긴 디코드 문맥을 여러 GPU에 분산 | GPU당 부담은 줄지만 토큰과 문맥을 교환하는 통신이 발생 |

실제 시스템은 여러 방식을 조합한다. 동일한 GPU 수에서도 조합에 따라 가중치가 분할되거나 복제되고, KV 캐시가 GPU별로 다르게 배치되며, 통신량도 달라진다. Frontier는 이러한 차이를 반영하여 구성별 메모리 여유와 처리 성능을 비교한다.

### 2.2.5 운영 정책

요청 처리 방식은 실제 LLM 서빙 소프트웨어인 vLLM V1의 주요 스케줄링 동작을 기준으로 모사한다. 요청은 도착 순서에 따라 대기열에 들어가며, 사용 가능한 메모리와 배치 한도 내에서 여러 요청을 계속 묶어 처리한다. 긴 입력은 여러 번으로 나누어 처리하고, 메모리가 부족하면 처리 중인 요청을 중단한 뒤 이후에 문맥을 다시 계산할 수 있다.

구성에서는 한 번에 처리할 요청과 토큰의 범위, 긴 입력의 분할 처리 여부, 메모리 부족 시 요청 처리 방식, 세션 캐시 유지, 요청 분배 정책 및 CPU DRAM 활용 여부를 설정한다. 이러한 정책은 동일한 하드웨어에서도 메모리 점유, 캐시 적중, 재계산량 및 응답 지연을 변경한다. 제2.3절에서는 이 설정들이 시간축에서 어떻게 작동하는지 설명한다.[^implementation-contract]

## 2.3 시간축 기반 시뮬레이션 방식

Frontier는 이산 사건 시뮬레이션(Discrete-Event Simulation, DES) 방식을 사용한다. DES는 시스템 상태가 바뀌는 시점만 사건으로 기록하고, 사건을 시간 순서대로 처리하는 방법이다.

예를 들어 요청이 도착한 시점, 배치 처리가 끝난 시점, KV 데이터 전송이 완료된 시점에는 대기열이나 메모리 상태가 달라진다. 반면 그 사이에 아무 변화가 없다면 해당 구간을 반복 계산하지 않고 다음 사건 시점으로 바로 이동한다. 이를 통해 수시간의 서비스 운영과 대규모 시스템을 일반 CPU 환경에서 비교적 빠르게 재현할 수 있다.

```text
요청 도착
  → 대기열 배치
  → 처리할 요청 묶음 구성
  → 프리필·디코드 실행
  → KV 캐시 저장·이동·회수
  → 요청 완료
```

LLM 서비스에서는 처리 속도와 메모리 상태가 서로 영향을 준다. 처리가 늦어지면 더 많은 요청과 KV 캐시가 시스템에 남고, 메모리 여유가 줄면 대기와 재계산이 증가해 처리가 다시 늦어질 수 있다. Frontier는 이와 같은 연쇄 변화를 시간축에서 연결하여 정적인 평균 계산으로 확인하기 어려운 순간적인 병목을 재현한다.[^frontier-paper]

주요 재현 대상은 다음과 같다.

- 여러 요청을 묶어 처리하는 연속 배치
- 긴 입력을 나누어 처리하는 청크 프리필
- 메모리 부족에 따른 요청 중단과 문맥 재계산
- 동일 세션의 기존 문맥 재사용
- GPU에서 밀려난 KV 캐시의 CPU DRAM 저장과 복원
- 분리형 시스템의 프리필·디코드 간 KV 데이터 전송

개별 GPU 명령이나 커널 내부 동작까지 재현하지 않고, 요청·배치·데이터 전송 단위의 실행 시간과 자원 변화를 모델링한다. 이와 같은 고수준 추상화를 통해 절대 성능의 일부 정확도를 양보하는 대신 장시간 워크로드와 다수의 설계 조합을 빠르게 비교한다.

TraceLab 기반 기준 실험에서는 16,333초(약 4.54시간)의 가상 서비스 운영 중 완료된 요청 93,571건을 347.72초에 재현하였다.[^performance-example] 실행 시간은 워크로드와 분석 장비에 따라 달라지며, 이 결과는 시뮬레이터의 처리 규모를 나타내는 참고값이다.

동일한 설정과 워크로드는 동일한 결과를 생성하며, 최종 입력 조건도 결과와 함께 보관한다. 이를 통해 구성 간 비교 결과를 재현하고 변경 원인을 추적할 수 있다. 절대 처리량과 지연은 분석 모델의 가정을 포함하므로, 최종 사양 결정 전에는 확보 가능한 실측값이나 상세 분석을 이용한 보정이 필요하다.

## 2.4 분석 결과와 활용 절차

분석 결과는 메모리 자원의 변화가 실제 서비스에 미치는 영향을 다음 순서로 연결한다.

```text
메모리 용량·대역폭 변경
  → 캐시 적중·축출·재계산 변화
  → 대기열과 처리 효율 변화
  → 응답 지연과 처리량 변화
```

### 2.4.1 주요 분석 결과

| 분석 영역 | 주요 결과 | 활용 목적 |
| --- | --- | --- |
| GPU 메모리 | KV 캐시 여유, 시간별 점유 변화, 최대 점유 | 메모리 부족이 시작되는 시점과 필요 용량 확인 |
| 메모리 부족 비용 | 캐시 축출, 요청 중단, 재계산된 토큰과 추가 지연 | 용량 부족이 연산 낭비와 서비스 저하로 이어지는 영향 확인 |
| CPU DRAM 효과 | CPU 캐시 점유·적중, GPU와 CPU 간 전송량과 지연 | CPU DRAM 추가 효과와 적정 용량·대역폭 검토 |
| 서비스 성능 | 처리량, 첫 응답 시간(TTFT), 토큰 생성 간격(TPOT), 전체 응답시간 | 메모리 증설 효과를 고객 서비스 지표로 환산 |

응답 지표는 평균뿐 아니라 p50·p90·p99를 함께 제시한다. 이를 통해 전체 요청의 일반적인 성능과 일부 긴 요청 또는 혼잡 시간대의 성능을 구분하여 평가한다.

### 2.4.2 표준 분석 절차

구성 비교는 다음 절차로 수행한다.

1. 고객 워크로드와 현재 시스템을 기준 구성으로 설정한다.
2. HBM, CPU DRAM, 전송 대역폭 또는 시스템 구성 중 비교할 변수를 선정한다.
3. 다른 조건은 유지하고 대상 변수만 단계적으로 변경한다.
4. 메모리 사용, 재계산량, 처리량 및 응답 지연을 함께 비교한다.
5. 서비스 목표를 만족하면서 자원 사용과 성능의 균형이 우수한 후보를 선별한다.
6. 추가 자원의 효과가 줄어드는 지점과 다음 병목을 확인한다.
7. 최종 후보를 상세 시뮬레이션 또는 실장비 검증 대상으로 선정한다.

단일 지표가 가장 좋은 구성을 자동으로 최적안으로 판단하지 않는다. 예를 들어 처리량이 높더라도 응답 지연 목표를 충족하지 못하면 후보에서 제외한다. 서비스 목표를 만족하는 구성 중 메모리 투입 대비 개선 효과가 큰 후보를 우선 검토한다. 이는 논문에서 제시한 서비스 수준 제약 기반 설계 탐색 개념을 현재 분석 목적에 맞게 단순화한 것이다.[^frontier-paper]

### 2.4.3 결과 해석 기준

| 관측 결과 | 주요 해석 |
| --- | --- |
| GPU 메모리 점유와 재계산이 함께 증가 | KV 캐시 용량 부족 가능성 |
| GPU 메모리에 여유가 있지만 대기와 토큰 생성 지연이 증가 | 연산 또는 통신 병목 가능성 |
| CPU 캐시 적중은 증가하지만 첫 응답 시간 개선이 제한적 | 데이터 복원 또는 다른 처리 단계가 병목일 가능성 |
| 메모리를 늘려도 재계산과 응답 지연이 더 이상 개선되지 않음 | 필요한 용량이 충족되었거나 병목이 다른 자원으로 이동 |

병목은 하나의 지표만으로 판단하지 않고 메모리 점유, 재계산, 전송, 대기 및 응답 지표의 변화를 함께 검토한다.

## 2.5 개발 성과 및 적용 범위

현재의 C++ 코어는 기존 Python 시뮬레이터의 핵심 동작을 포팅한 뒤, 대규모 반복 분석과 메모리 제품 검토에 필요한 기능을 추가로 확장한 결과다. 기존 Python 구현은 프로파일링과 일부 Python 전용 기능을 위해 유지하며, 신규 메모리 분석은 C++ 코어를 기준으로 수행한다.[^cpp-transition]

| 개선 영역 | 주요 개선 내용 | 분석 관점의 효과 |
| --- | --- | --- |
| 실행 속도 | C++ 기반 사건 처리와 상태 관리를 적용하여 동일 조건의 내부 비교에서 시뮬레이션 실행 속도를 10배 이상 개선 | 장시간 워크로드와 다수의 설계 조합을 반복 분석할 수 있는 처리 여력 확보 |
| CPU 메모리 활용 | GPU에서 밀려난 KV 캐시를 유한 용량의 CPU DRAM에 저장하고, 대역폭과 지연을 반영해 복원하는 기능 추가 | CPU DRAM 용량·대역폭에 따른 재계산 절감과 응답 개선 효과 비교 |
| 멀티턴 세션 | 세션과 대화 순서를 유지하고 요청 간 간격을 반영하며, 후속 요청에서 기존 KV 캐시를 재사용하는 기능 추가 | 에이전틱 AI의 반복 호출과 장시간 세션에서 캐시 보존 효과 분석 |
| 모델 구조 확장 | MLA와 KDA·MLA 하이브리드 구조를 지원하고, 토큰별 KV와 세션 단위 상태를 구분하여 관리 | 최신 모델 구조에 따른 메모리 크기와 증가 방식의 차이 반영 |
| 메모리 사양 분석 | 물리 HBM, 모델 가중치, 정밀도 및 병렬화를 반영한 KV 캐시 용량 산정과 시간별 점유 기록 추가 | 메모리 제품의 용량·대역폭 변화와 서비스 성능의 관계를 직접 비교 |

이러한 개선을 통해 분석 범위가 기본 요청 처리와 GPU 중심 분석에서, 멀티턴 세션과 GPU–CPU 메모리 계층을 포함한 고객 서비스 수준으로 확대되었다.

현재 C++ 코어는 통합형과 순차형 프리필-디코드 분리, 주요 병렬화 방식, 세션 캐시 및 CPU KV 오프로딩을 중심으로 분석한다. 일부 sparse attention, 어텐션-FFN 분리 및 speculative decoding 등은 현재 범위에 포함하지 않는다.[^implementation-contract]

Frontier는 실장비 검증을 대체하는 도구가 아니라, 초기 기획 단계에서 메모리 병목을 식별하고 상세 검증이 필요한 후보를 좁히는 분석 도구로 활용한다. 제3장에서는 HBM과 CPU DRAM의 용량·대역폭을 변경한 사례를 통해 분석 결과와 의사결정 과정을 설명한다.
